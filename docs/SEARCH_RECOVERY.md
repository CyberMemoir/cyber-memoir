# 搜索等待、分数复用与版本检查

本轮选择性适配 [PR #14](https://github.com/CyberMemoir/cyber-memoir/pull/14) 中已有的搜索等待和重排分数复用代码、回归测试。核对时该 PR 的 head 为 `bed382ad3b1eca4ed0324b3d5ccb248f3dc97aec`，仍未合并；本轮没有合并其数据、评测检查点或其他 389 个改动文件，也没有自动批准文化记录。

交互参考 [Algolia 的性能指南](https://www.algolia.com/doc/guides/building-search-ui/going-further/improve-performance/js)中的加载反馈与重复请求优化，但本库不缓存搜索事实或最终回答。保留现有星空设计，不安装 Algolia 或改成按键自动抓取/检索。

## 搜索与回答分阶段

- 搜索完成后立即显示结果并解除搜索按钮的等待状态，进入索引的位置不再等到回答完成。
- 回答单独显示“正在整理证据回答”，失败或超时保留检索结果。重试回答仅请求回答接口，使用该次提交捕获的查询与平台，不采用尚未提交的输入框修改。
- 每个阶段最多等待五分钟；网关可以更早返回错误。取消和提交新查询会终止浏览器请求并使旧响应失效，不承诺中断服务端已经开始的模型计算。
- 回答阶段可以使用已有结果或发起新查询；分页按钮暂时禁用，避免分页请求与回答共用请求所有权。分页失败重试仍保持原查询/平台/offset，已有回答不会重算或清空。
- 页面离开后取消请求。初次目录加载不移动页面；从搜索框提交的查询在检索结果到达时才定位到索引。

## 只复用重排分数

单进程最多保存 64 组分数，保留五分钟。键包含模型路径/标识、线程配置、查询、候选文本及其顺序，并持有模型提供函数的对象引用，避免替换函数后对象 ID 重用造成命中旧缓存。

所有计算与缓存操作仍经过原来的串行锁。相同排队请求复用校验过的分数；不同请求仍逐一执行模型。返回列表是副本，调用方无法改写缓存。只接受数量与候选一致、有限且位于 `[0,1]` 的归一化分数；异常结果不缓存，不伪装成已校准评分。

每次检索重新读取权限、当前公开修订、证据及引用。模型路径必须指向不可变快照；在同一路径替换权重后应重启服务，不能拿旧模型实例或旧分数当新模型结果。换嵌入模型仍需索引重建，本次没有改变向量空间。

## 长请求期间的内容变动

加入评分前后的版本与候选有效性核对：

1. 记录实际参与检索的条目修订。
2. 评分后重新检查当前公开状态、修订、证据 chunk 和平台/日期过滤条件。
3. 重新核对精确别名/来源身份命中，不能让旧身份或旧过滤条件绕过当前资格。
4. 公开详情刷新 SQLAlchemy 的会话实体；不能因 identity map 预先加载过条目而继续读旧修订。
5. 读取详情时再次核对版本。评分期间被替换、撤回或合并的候选不使用旧分数解释新断言，返回 `corpus_changed_during_search`。

页面对这种降级显示明确原因与“刷新当前检索”，刷新使用原提交内容。空结果时不把内容变动误写成“缺少证据”，也不直接引导用户补造来源。查询完成后再次发生的变动不属于冻结快照保证，分享与阅读仍遵循当前公开修订规则。

## 本轮证明了什么

后端回归使用合成归一化评分器，而非真实模型：相同并发输入六个调用只计算一次，不同查询六个调用仍逐一计算；查询、文本、顺序、模型配置与 TTL 变化不复用；容量上限、返回副本、NaN/无穷/越界/数量错误、搜索—回答复用与撤回立即生效得到覆盖。另有不同会话修改修订、评分中发布新修订的回归，避免把旧分数用于新事实。

浏览器回归覆盖阶段等待、五分钟搜索/回答超时、取消、独立回答重试、新查询排除旧响应、捕获提交参数、分页兼容与语料变化刷新。所有夹具均明确标记为合成材料，没有写业务数据库、修改人工金标准或启动真实平台采集。

这些结果证明请求所有权和复用机制，不证明真实 BGE 延迟、吞吐或语义召回。本轮没有下载模型权重、启动付费 GPU 或报告新的检索效果指标。

2026-10-09 最终结果：后端全量 156 项通过、真实服务集成 1 项按环境跳过；浏览器全量 39 项通过；Ruff、Prettier、TypeScript、Next.js production build 和差异格式检查通过。先前导入、双向引用与审核自动队列回归也在全量套件中通过。

## 查询向量精确复用（2026-10-10 接续）

参考 [RedisVL 的 embedding 精确键、模型身份与 TTL 缓存](https://redis.io/docs/latest/develop/ai/redisvl/user_guide/how_to_guides/embeddings_cache/)，只借用做法，不新增 RedisVL 依赖或要求 Redis 在线。查询阶段改用 `embed_query`，索引文档批处理仍走原 `embed`，不把公开内容、资格、候选或回答放进向量缓存。

- 单进程最多 64 条、300 秒 TTL/LRU。键绑定原查询文本、不可变模型路径、设备、线程数和提供函数对象；搜索先沿用原有 NFKC/casefold/空白规范化，再传入原推理文本，不作“语义相似缓存”。键只保留 SHA 而不是查询明文，不持久化。
- 缓存填充与批处理共享原 embedding 串行锁，相同排队查询只编码一次，不同查询和索引仍顺序执行；冷加载也在锁内。
- 只有通过维度/数量/有限数校验的向量能入缓存。返回列表是副本；无效推理不缓存，下次可重试；关闭 backend 不返回旧缓存。
- 每次请求仍执行实际数据库资格、公开修订、chunk、证据和过滤条件检查，重排分数复用规则不变。权重须在不可变路径，替换同路径文件后应重启，切换向量空间须重建索引。

### 真实 BGE 测量

用已验证固定 BGE-M3 快照、原公开归档 gold 的 25 个规范化查询，在 CPU/4 线程/FP32 比较原始逐查询编码、缓存首次计算与重复命中。**25/25 向量逐元素完全相同**。暖态中位数：原始 **75.141ms**，首次缓存计算 **72.015ms**，重复命中 **0.023ms**。包装真实 `encode` 计数、不替换模型输出：六个相同并发请求实际编码 **1 次**，六个不同请求编码 **6 次**，两者推理峰值均为 1。

这只省掉每次重复查询约 **0.075 秒的向量推理**，并不能解释或解决上轮 **18.359 秒** 的检索/回答 POST 合计耗时。不是 HTTP 加速倍数、生产 SLA 或回答质量提升；下一步应测候选交叉重排等阶段。该开发机非专用性能机器，数字不作为跨硬件承诺。没有重写正负例、改变阈值、重跑文化审批或修改业务部署。
