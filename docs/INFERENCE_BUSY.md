# 有限等待、忙碌提示与明确重试

用户选择优先“减少并发等待，加入忙碌提示和重试”。本轮据此前真实六请求测量的最大 44.952 秒模型锁等待，实现有限等待和缓存快速读取，不以跳过评分或放宽 0.35 下限换取成功。

## 服务协议

采用 [RFC 9110 的 503 临时不可用与 Retry-After 语义](https://www.rfc-editor.org/rfc/rfc9110.html#name-503-service-unavailable)：模型槽等待超过预算时，search/answers 返回 **503**，`code=inference_busy`、中文 `detail` 和 `retry_after_seconds`，并发送同值 `Retry-After`、`Cache-Control: no-store`。预算默认 `INFERENCE_QUEUE_TIMEOUT_SECONDS=2`，配置只接受有限的 **0–60 秒**；0 表示立即拒绝忙碌槽。建议等待不是完成时间承诺。

- 各查询推理阶段分别限制锁等待，不中断已经开始的计算。不是“所有 HTTP 两秒完成”的保证。
- 独立短缓存锁保护 TTL/LRU/副本；有效向量和分数命中在模型锁之前返回，不被无关计算挡住。miss 获得模型槽后再次查缓存，相同输入仍只计算一次。
- 未获槽位不加载/执行该阶段模型。重排拒绝可能发生在查询 embedding 已计算之后；不能据此声称拒绝请求完全没计算模型。
- `InferenceBusy` 必须传播到 HTTP，不能吞成 vector/reranker unavailable 后返回未评分成功或“无证据”。既有公开资格、修订/证据检查与有限分数校验保留。
- 索引文档批处理仍由原 worker/job 期限控制，不在队列繁忙时把批处理当查询拒绝。单进程模型串行计算约束仍在，不宣称增加吞吐或跨进程全局限流。

OpenAPI/TypeScript 契约已声明两个接口的 503 body 和 Retry-After。CORS 显式暴露该头；实际 Next rewrite 的头/body 传递有浏览器回归。

## 前端行为

已有灰色错误框和薄荷文字按钮，不新增图卡或改变星空设计。明确忙碌时显示服务文字与禁用的重试倒计时；到建议时间后恢复按钮，**不自动发请求**。没有定时轰炸后端，也不将建议时间写成预计完成进度。

- 搜索保留已有结果；重试使用失败提交捕获的 query/platform/offset，而不是随后在输入框键入的内容。
- 回答忙碌保留检索结果；重试只调用回答接口，不重新搜索，仍使用捕获参数。
- 新提交/取消/页面离开撤销旧请求所有权和倒计时，不让晚到的忙碌响应覆盖新查询。
- 支持 delta-seconds/HTTP-date Retry-After，头缺失或损坏时使用 body 建议；客户端最多等 60 秒。一般错误不冒充 `inference_busy`。

## 真实模型与 HTTP 验证

新独立标签/tmpfs PG/OpenSearch 使用原批准快照，实际 BGE-M3/reranker CPU/4 线程/FP32。预热不同查询，观察一个新查询的实际 compute-start 标记，再提交五个其它查询，期间读取已缓存的原查询：

| 请求 | 观察结果 |
|---|---|
| 已获槽位的新查询 | 200，15.604s，计算未被抢占 |
| 五个其它新查询 | 全部明确 503，HTTP 3.086–3.695s；不是五个完成的搜索 |
| 该计算尚未结束时的缓存查询 | 200，0.284s；确认在无关计算完成之前返回，无新模型计算 |
| 槽位释放后明确重试 | 200，8.966s，正常评分 |

拒绝请求各自已经计算 embedding，共 **5 次**，但没有执行 cross-encoder。初版探针错误地断言“所有模型都没计算”而失败；修正为独立验证重排准入，并保留真实 embedding 次数，不掩饰这项成本。

这不是旧“六个请求全部成功、最慢 54.616s”到“五个 503”的等价吞吐提速，也不是生产 SLA。共享开发机上后台构建/测试有活动，HTTP 时间还包括 embedding、数据库、传输等，不将它等同于两秒锁预算。

探针后同一快照的正常 25 用例完整跑通、无失败/降级：Recall@10 **14/14**、MRR **0.8512**、回答含目标 **8/14**、负例弃答 **11/11**。逐用例断言/引用与原 hybrid 报告完全一致；16 条语义仍待人工复核，六条正例弃答未解决。该轮有探针预热缓存，仅用于质量保持检查，不再当全新查询的延迟样本。

## 复现

按 [归档评测](ARCHIVE_EVALUATION.md) 在全新隔离服务恢复/索引，不迁移或重启业务栈。正常 CPU/API 使用默认两秒准入预算，开启只供评测的 trace：

```bash
INFERENCE_QUEUE_TIMEOUT_SECONDS=2 "$MODEL_PY" ops/archive_eval_server.py \
  --snapshot "$SNAP" --run-id "$RUN" --database-url "$DB" \
  --search-url http://127.0.0.1:59201 --pg-container "$PG" --search-container "$OS" \
  --mode hybrid --trace-inference
# 另一终端，新的输出文件：
apps/backend/.venv/bin/python evals/busy_probe.py \
  --snapshot "$SNAP" --run-id "$RUN" --out "$SNAP/busy-report.json"
```

保存该时刻的 trace 后再运行其它用例，或使用新的 trace/进程。原离线定义/容量探针显式用 **60 秒**等待预算来观察六次原始串行计算，并在报告记录该设置；它不是生产两秒准入验收，不混淆两种目的。原 HTTP 六并发全成功基线是历史代码下的结果，不能用新的忙碌拒绝样本覆盖。
