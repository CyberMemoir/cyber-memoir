# 逐字段审核与证据绑定

工作台参考 [Wikidata 的逐条断言引用做法](https://www.wikidata.org/wiki/Help:Sources)：来源需要支持具体断言，而不是只要登记了一个来源，就把它附到全部字段。这里保留 Cyber Memoir 的人工审核、版本冲突和未知起源规则，不复制它的界面或素材。

## 核对流程

1. 逐份打开原文、定位说明与原平台来源，判断材料实际支持什么；来源链接存在本身不是支持证明。
2. 在材料下分别勾选 **支持定义**、**支持使用语境**。同一材料确实支持两个完整字段时，才同时勾选两项。
3. 修改定义或语境文字后，该字段原先的勾选会清空；另一个字段不受影响。重新选择支持改后完整文字的材料，再作人工确认。
4. 尚未选择证据的文字可以保存为待审草稿，不会生成 `evidence_ids: []` 的伪支持断言，也不会发布。发布前会提示缺少哪个字段的完整支持。
5. 核对高级结构化编辑中的反对意见、起源、局部补充断言、事件与关系，再填写理由并确认。修改文字、引用或结构化内容均会取消人工确认；保存或提交审核请求进行中不允许继续改写表单。

高级编辑可显式填写完整支持，例如 `key: "definition"`、与完整字段一致的 `statement`、`stance: "supports"` 和实际 `evidence_ids`。它仍受后端 schema 与发布规则校验，不是跳过审核的通道。

## 原有引用与跨来源材料

- 初始化只读取对应字段、完整文字且 `stance: supports` 的引用，不把起源、反对意见或另一字段的材料自动选入。
- 保存时保留反对与局部补充断言，不把它们抹掉或改成支持。不同字段的材料不自动合并。
- Worker 候选除显示最初来源的材料外，还加载所有 claims/events/relations/导入中引用的其他来源材料。跨来源的反对意见不能只留一个看不见的 ID。
- 切换稿件、令牌或离开页面会取消旧的材料加载，旧响应不能更新新编辑器。
- **追加用法**的旧字段与引用保持只读；完整保留原有支持/反对绑定。新增用法、时间和关系在高级编辑中核对，后端再次校验追加边界。

勾选和结构校验不自动判断语义蕴含，也不证明材料真实；“材料是否支持完整断言”仍是审核者需要核对的内容。

## 回归验收

`apps/web/e2e/review-fields.spec.ts` 使用合成材料与实际临时后端：

- 原实现被测试复现为：保存未修改的稿件时，三个不同用途的材料被一并写入定义和语境，反对/局部断言被丢弃。
- 修复后验证初始引用、独立选择、编辑后重新选引、保留反对意见、缺少支持不提交发布、人工确认失效、实际发布后的精确绑定及夹具撤回。
- Worker 跨来源场景先复现只显示最初来源，再验证所有已引用材料都能核对。
- 纯函数回归覆盖空引用草稿、追加保护、完整/局部/反对断言区分及同一字段去重。

浏览器夹具使用独立客户端地址隔离不同测试场景的限流预算；这一映射只存在于 `ops/e2e_server.py`，生产 API 不读取该测试头，也不信任任意 `X-Forwarded-For`。单独回归确认同一测试客户端的第 61 次请求仍返回 429；未放宽或关闭生产限流。

复现：`cd apps/web && npx playwright test e2e/review-fields.spec.ts`；完整检查见 [验证记录](VERIFICATION.md)。
