# 逐字段审核与证据绑定

工作台参考 [Wikidata 的逐条断言引用做法](https://www.wikidata.org/wiki/Help:Sources)：来源需要支持具体断言，而不是只要登记了一个来源，就把它附到全部字段。这里保留 Cyber Memoir 的人工审核、版本冲突和未知起源规则，不复制它的界面或素材。

## 核对流程

1. 逐份打开原文、定位说明与原平台来源，判断材料实际支持什么；来源链接存在本身不是支持证明。
2. 在材料下分别勾选 **支持定义**、**支持使用语境**。同一材料确实支持两个完整字段时，才同时勾选两项。
3. 修改定义或语境文字后，该字段原先的勾选会清空；另一个字段不受影响。重新选择支持改后完整文字的材料，再作人工确认。
4. 尚未选择证据的文字可以保存为待审草稿，不会生成 `evidence_ids: []` 的伪支持断言，也不会发布。发布前会提示缺少哪个字段的完整支持。
5. 核对高级结构化编辑中的反对意见、起源、局部补充断言、事件与关系，再填写理由并确认。修改文字、引用或结构化内容均会取消人工确认；保存或提交审核请求进行中不允许继续改写表单。

高级编辑可显式填写完整支持，例如 `key: "definition"`、与完整字段一致的 `statement`、`stance: "supports"` 和实际 `evidence_ids`。它仍受后端 schema 与发布规则校验，不是跳过审核的通道。

## 原有引用与跨来源材料

- 初始化只读取对应字段、完整文字且 `stance: supports` 的引用，不把起源、反对意见或另一字段的材料自动选入。
- 保存时保留反对与局部补充断言，不把它们抹掉或改成支持。不同字段的材料不自动合并。
- Worker 候选除显示最初来源的材料外，还加载所有 claims/events/relations/导入中引用的其他来源材料。跨来源的反对意见不能只留一个看不见的 ID。
- 切换稿件、令牌或离开页面会取消旧的材料加载，旧响应不能更新新编辑器。
- **追加用法**的旧字段与引用保持只读；完整保留原有支持/反对绑定。新增用法、时间和关系在高级编辑中核对，后端再次校验追加边界。

勾选和结构校验不自动判断语义蕴含，也不证明材料真实；“材料是否支持完整断言”仍是审核者需要核对的内容。

## 回归验收

`apps/web/e2e/review-fields.spec.ts` 使用合成材料与实际临时后端：

- 原实现被测试复现为：保存未修改的稿件时，三个不同用途的材料被一并写入定义和语境，反对/局部断言被丢弃。
- 修复后验证初始引用、独立选择、编辑后重新选引、保留反对意见、缺少支持不提交发布、人工确认失效、实际发布后的精确绑定及夹具撤回。
- Worker 跨来源场景先复现只显示最初来源，再验证所有已引用材料都能核对。
- 纯函数回归覆盖空引用草稿、追加保护、完整/局部/反对断言区分及同一字段去重。

浏览器夹具使用独立客户端地址隔离不同测试场景的限流预算；这一映射只存在于 `ops/e2e_server.py`，生产 API 不读取该测试头，也不信任任意 `X-Forwarded-For`。单独回归确认同一测试客户端的第 61 次请求仍返回 429；未放宽或关闭生产限流。

复现：`cd apps/web && npx playwright test e2e/review-fields.spec.ts`；完整检查见 [验证记录](VERIFICATION.md)。

## 修订对照与编辑冲突

借鉴 [Wikipedia 的修订差异对照](https://en.wikipedia.org/wiki/Help:Diff) 与 [编辑冲突处理](https://en.wikipedia.org/wiki/Help:Edit_conflict)：显示旧/新内容，保留用户未提交的文字，让审核者明确决定如何继续；不自动合并文化断言。

- 编辑器对照原先已批准的基准修订与当前本地稿；新条目明确没有公开基准。基准快照缺失时说明不可计算，不当作空白稿。
- 对照覆盖名称、别名、定义、语境、起源状态、断言/引用、事件和关系。引用顺序、同一支持组中的重复 ID 不制造变更；支持变反对、删除证据等会显示。结构化对照不是语义真实性判断。
- 版本管理可选择任意两份历史稿对照，查看审核理由、审核者与时间。起草新修订绑定历史记录本身的 Meme ID，不使用后来改填的输入框值。
- 历史记录只对审核者开放；读历史或创建待审稿不恢复公开资格。条目已撤回时，界面提示并明确确认重新发布；已合并条目不能发布。
- 遇到冲突，服务器不接受过期写入，编辑器保留本地字段和高级编辑文字。可以复制不含令牌的本地编辑副本、对照最新服务器稿，明确采用最新写入基准后重新核查；读取服务器稿会要求确认放弃本地改动。
- 另一位编辑者处理稿件后，队列轮询不自动丢弃正在编辑的副本。已处理稿件不可继续写入；自己的审核成功后才自动切换下一稿。
- 复制副本只是当前编辑状态，不是已批准文件，也不承诺跨页面自动保存；高级 JSON 语法/数组格式错误时保留原文字，不使整个编辑器崩溃。

### 版本化 API（必须同步升级客户端）

保存与审核决定现在要求具体的 `If-Match`。参考 [HTTP 条件请求](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match) 使用强 ETag；本审核协议只接受单个具体标签，不允许 `*`、弱标签或标签列表绕过确定稿件的核查。

1. 读取 `GET /v1/reviews/{revision_id}`：正文 `etag` 与响应 `ETag` 一致。队列中的每一稿也包含 `etag` 和 `edit_version`。
2. `PUT /v1/reviews/{revision_id}` 保存草稿时，传递读取时的 `If-Match`；成功返回新的稿件与新标签，即使内容相同也递增编辑版。
3. `POST /v1/reviews/{revision_id}/decision` 必须使用**刚保存那份稿件**的标签，不能重新获取另一份稿件的最新标签后直接批准它。
4. 缺少标签返回 **428**；过期或父条目公开状态改变返回 **412**，不写入。已处理稿件返回 **409**，业务字段/证据仍按原有规则校验。失败事务不会消耗编辑版。
5. ETag 同时绑定稿件编辑版与父条目的公开修订/状态；撤回后，旧页面不能无声地重新公开条目。采用最新标签不会改变稿件的 `based_on_revision`，不能自动变基。

`GET /v1/reviews/{revision_id}/comparison` 返回原基准、当前已批准内容、当前稿与公开状态。该接口需要审核令牌，不提供公共历史档案绕过权限。

写入采用数据库条件更新与事务锁，SQLite 的真实双连接竞争回归已验证一个成功、一个 412；真实 PostgreSQL 同样的双连接测试已加入 `test_live_stack.py`，需以当前提交的 CI/integration 结果为准。
